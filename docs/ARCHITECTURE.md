# Архитектура

## Приложения

| Приложение | Ответственность |
|---|---|
| `documents` | документы, извлечение текста, индексация, поиск, рубрики, история поиска |
| `users` | кастомная модель пользователя, вход по email, подтверждение почты, сброс пароля |
| `config` | настройки, маршруты, health-эндпоинты |

Внутри `documents` намеренно выделены небольшие модули с одной задачей:

- `constants.py` — единые ограничения (рубрики, длины, типы и размер файла) и
  функции проверки. Единственное место, где описаны правила;
- `utils.py` — извлечение и очистка текста; принимает и путь, и файловый объект;
- `documents.py` — описание индекса Elasticsearch;
- `signals.py` — индексация и сброс кэша после сохранения (best-effort);
- `rubrics.py` — сборка списка рубрик и его кэш;
- `services/search_service.py` — построение и выполнение поискового запроса;
- `rate_limit.py` — ограничение частоты на общем кэше.

## Модель данных

```text
User (users.User)                     Document (documents.Document)
├── email (USERNAME_FIELD, unique)    ├── user           → User (CASCADE)
├── first_name, last_name             ├── rubrics        JSONField, список строк
├── is_active, is_staff, is_moderator ├── text           TextField (извлечённый текст)
├── is_email_verified                 ├── is_public      BooleanField
├── email_verification_token          ├── created_date   auto_now_add
├── reset_password_token              ├── file           FileField, documents/%Y/%m/%d/
└── reset_password_token_created_at   ├── file_name      исходное имя файла
                                      ├── file_type      pdf | docx | xlsx | txt
SearchHistory                         └── text_source    file | manual
├── user → User (CASCADE)
├── query
├── results_count
└── created_at
```

Документ — единственный источник правды. Индекс Elasticsearch `documents`
пересобирается из таблицы командой `manage.py search_index --rebuild -f` и в любой
момент может быть удалён без потери данных.

Ограничения заданы в `documents/constants.py`: до 10 рубрик, до 100 символов в
рубрике, до 100 000 символов текста, файл до 20 МБ одного из четырёх типов.
Лимит файла совпадает с `client_max_body_size` в nginx.

## Создание документа

```text
POST /documents/create/ (или /api/documents/)
  → проверка частоты запросов (Redis; при отказе — пропуск, fail-open)
  → проверка рубрик, текста и файла (documents/constants.py)
  → извлечение текста из загруженного файла (utils.py)
  → одна запись Document в PostgreSQL
  → ответ 302 (веб) или 201 (API)
  ─── после коммита транзакции ───
  → индексация в Elasticsearch        (ошибка только в лог)
  → сброс кэша рубрик владельца       (ошибка только в лог)
```

Текст извлекается **до** сохранения, из самого загруженного файла. Раньше
документ записывался дважды: сначала пустой, потом с текстом, прочитанным обратно
с диска по пути `MEDIA_ROOT` — и при несовпадении пути текст молча оставался
пустым.

## Почему индексация best-effort

Автоматические сигналы `django-elasticsearch-dsl` пишут в Elasticsearch без
обработки ошибок, и исключение выходит прямо из `Document.save()`. При
недоступном Elasticsearch создание документа отвечало 500, хотя строка в
PostgreSQL уже была вставлена.

Поэтому:

- в описании индекса стоит `ignore_signals = True`, а в настройках —
  `ELASTICSEARCH_DSL_AUTOSYNC = False`: библиотека в реальном времени не пишет;
- индексация выполняется в `documents/signals.py` через `transaction.on_commit`
  и любые ошибки оставляет в логе;
- `search_index --rebuild` при этом работает как раньше: он не зависит от
  сигналов.

Обратная сторона: индекс может отстать от базы. Документ, созданный при
недоступном Elasticsearch, найдётся только после переиндексации — состояние
видно в `/health/ready/` как `elasticsearch: degraded`.

## Поиск

```text
POST /search/results/ (или /api/search/)
  → multi_match по text и rubrics с fuzziness=AUTO
  → фильтр доступа: свои документы или публичные
  → фильтры по рубрике и приватности
  → сортировка в Elasticsearch: _score | -created_date | created_date
  → пагинация, подсветка фрагментов
  → запись в SearchHistory (только первая страница)
```

Сортировка выполняется Elasticsearch, а не списком результатов в Python: иначе
упорядочивалась бы только текущая страница, а не весь найденный набор.

Сервис поиска возвращает `SearchResponse` с результатами и метаинформацией, а
представления решают, что показать при отказе Elasticsearch: веб-интерфейс
показывает «Поиск временно недоступен», API — ошибку.

## Кэш

Кэшируется только список рубрик — под ключом `rubrics_user_<id>` с TTL 300 секунд.
Страница целиком не кэшируется: `cache_page` без `vary_on_cookie` отдавал одному
пользователю разметку, собранную для другого, вместе с чужими названиями рубрик.

Ключ явный, поэтому сбрасывается через `cache.delete` на любом бэкенде. Прежняя
инвалидация опиралась на Redis-специфичный `delete_pattern` и на фиктивные ключи
`cache_page`, которые никогда не совпадали с реальными.

## Отказы зависимостей

| Что упало | Что происходит |
|---|---|
| PostgreSQL | приложение не работает, `/health/ready/` отдаёт 503 |
| Redis | кэш и лимиты не работают, лимиты пропускают запросы (fail-open), `/health/ready/` — `degraded` |
| Elasticsearch | документы создаются и читаются, поиск отвечает «временно недоступен», `/health/ready/` — `degraded` |

Проверки на эти сценарии — `tests/test_resilience.py`.

## Версия клиента Elasticsearch

Сервер — Elasticsearch 8.11, клиент — `elasticsearch` 7.17 и
`elasticsearch-dsl` 7.4. Ветка 7.17 официально совместима с сервером 8.x и
работает, но:

- клиент 8.x нужен для `dense_vector` и kNN, то есть для гибридного поиска;
- при включённой безопасности Elasticsearch 8 (xpack) потребуются креды, которых
  в настройках сейчас нет вовсе.

Обновление клиента — отдельная работа вместе с чанкингом и эмбеддингами.

## Поиск отрывков для потребителей

Форма границы зафиксирована в [SEARCH-CONTRACT.md](SEARCH-CONTRACT.md): потребителей
двое — Семён (служебный токен, только публичные документы) и лапот (персональный
токен, свои и публичные). Форма — решение, а не предложение: меняется вместе с
потребителями.

- **Куски в отдельном индексе `chunks`.** Один документ даёт десятки кусков,
  поэтому они лежат не в индексе `documents`, а рядом. Индекс производный:
  пересобирается командой `manage.py reindex_chunks` из текста документов и
  обновляется в `transaction.on_commit` вместе с документом.
- **Нарезка** — `documents/chunking.py` (чистая функция без зависимостей),
  сборка кусков — `documents/services/chunk_service.py::build_chunk_payloads`
  (тоже чистая, поэтому проверяется без Elasticsearch).
- **Кого видно** — решает токен, а не запрос: `user_id` в теле запроса
  отклоняется с 400. Служебный токен видит только `is_public=true`,
  персональный — ещё и документы своего пользователя.
- **Деградация.** Пока векторов нет, источник всегда `fulltext`. Когда появится
  векторная часть, недоступность модели эмбеддингов обязана давать `fulltext`, а
  не отказ; недоступность Elasticsearch — это `503`, а не пустой список: пустой
  список читается как «ничего нет».
- **Отпечаток версии** (`document_version`) — хеш текста документа. Ответ на
  §8.3 контракта: потребитель видит, что документ изменился и отрывок мог
  устареть, не перезапрашивая всё подряд.
- **Шкала `score`** — BM25, а не вероятность, и это внутренняя величина для
  сортировки и отладки. У векторного поиска шкала будет другая (косинусная
  близость), поэтому сравнивать `score` между разными значениями `source`
  нельзя. Порог отсечения настраивается в одном месте — `VECTOR_MIN_SCORE` в
  `documents/views/views_retrieve.py`.
